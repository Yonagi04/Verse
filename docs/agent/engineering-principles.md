# 工程设计基准

本规范把 SOLID、KISS、YAGNI、DRY 等原则转换为代码决策。原则服务于可维护性，不以类、接口或设计模式数量衡量质量。

## KISS 与 YAGNI

- 选择能完整满足当前需求的最简单设计；主流程应能被顺序阅读。
- 不为单一且稳定的实现预建接口、抽象类、Factory、Strategy、Context 或扩展框架。
- 不实现没有明确调用方的配置、钩子和通用能力。
- 简单不等于把所有逻辑放进同一类；混合职责、隐藏副作用同样不简单。
- 多 LLM Provider、路由策略、模型能力差异属于 Verse 已知变化点，可以显式抽象。

## DRY

- 业务规则、权限规则、错误映射、缓存键和 Provider 选择规则只能有一个权威实现。
- 消除“知识重复”，不要仅因两段短代码长得相似就提取通用工具。
- 偶然重复优先遵循三次原则；涉及安全、计费、幂等和数据一致性的不变量应尽早集中。
- 禁止复制已有方法后仅修改少量分支来支持新 Provider 或新业务类型。

## SOLID

### 单一职责 SRP

按变化原因划分职责：Controller 负责 HTTP 契约，Service 负责用例编排，领域策略负责业务决策，Mapper 负责持久化，Provider Adapter 负责外部协议适配。

出现以下组合通常需要拆分：HTTP 与数据库操作、业务编排与序列化、Provider 选择与 Provider 协议、远程调用与数据库事务、权限解析与跨租户资源操作。

### 开闭原则 OCP

- 对已知变化点建立小而清晰的接口；稳定编排依赖接口，不依赖具体 Provider SDK。
- 新增 Provider 或路由策略时，应主要增加实现和注册，不应在多个稳定服务中追加 Provider 名称分支。
- 修改类本身不等于违反 OCP；未知变化点不得为了“可扩展”而过度抽象。

### 里氏替换 LSP

- 同一接口的实现必须保持输入前置条件、输出保证和失败语义一致。
- 禁止以返回 `null`、静默跳过或抛出未约定的通用异常实现“不支持”。
- Provider 能力本质不同则拆分能力接口，不能让调用者通过类型判断恢复真实契约。

### 接口隔离 ISP

- 接口围绕调用者需要的能力设计，避免要求实现类提供无关或不支持的方法。
- Chat、Embedding、Rerank、Image、Audio、Streaming 等能力契约不同时应分离。
- 避免混合 CRUD、缓存管理、后台运维和外部调用的巨型 Service 接口。

### 依赖倒置 DIP

- 业务策略不直接依赖外部 SDK、Redis 客户端、HTTP 客户端或具体数据库细节。
- 第三方类型限制在 Adapter/Infrastructure 边界内，不能穿透到 Controller 和通用 Service 契约。
- 新代码优先构造器注入；禁止静态容器取 Bean 或在业务代码中查找 ApplicationContext。
- 不要求每个类都有接口；在外部边界、易变实现和测试替身确有价值时使用。

## 其他基础原则

- 组合优于继承；继承只用于稳定且可替换的 `is-a` 关系，不用基类充当工具箱。
- 遵循最少知识原则，避免跨越多个对象读取内部状态后在外部修改。
- 公开副作用：数据库写入、缓存变化、远程调用、事件发布和计费不能藏在 getter、构造器或转换器中。
- 快速失败：在边界校验输入，在权威位置维护业务不变量；禁止 catch 后只记录并继续。
- 默认不可变：DTO 组装和局部计算尽量减少共享可变状态。
- 优化需要证据；先保证正确和可观测，再根据延迟、吞吐、命中率等指标优化。

## 代码可读性信号

- 命名表达领域意图，避免含义不明确的 `handle`、`process`、`manage`、`CommonUtil`。
- 一个方法保持同一抽象层级；优先守卫语句，避免多层条件嵌套。
- Boolean 参数导致两种明显不同流程时，改为具名方法或策略。
- 过长参数列表、过多注入依赖、频繁跨对象取数据是职责混乱信号，需先分析而非机械拆分。
- 中文注释说明“为什么”和业务约束；代码能够表达的“做什么”不写注释。

## 修改历史代码

1. 先用测试固定待改行为和公共契约。
2. 不扩大已发现的跨层依赖、重复规则或巨型类问题。
3. 为安全实现需求，可以对直接触及的代码做最小必要重构。
4. 大范围重构必须单独规划迁移顺序、兼容风险和验收方式。
5. “遵循现有风格”只指合理的命名、协议和惯例，不代表复制已有缺陷。
