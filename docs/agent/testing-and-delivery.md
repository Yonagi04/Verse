# 测试与交付规范

## 当前 `src/test` 范围

在测试体系完成专项重写前，`src/test` 统一作为单元测试目录治理。新增测试以业务行为为单位，不以生产类数量、文件数量或覆盖率缺口为单位。

无需单独批准即可新增测试的对象：

- Service、应用用例和从 Service 提取的独立业务策略；
- Controller 的 HTTP 契约、参数校验、鉴权接入、响应和错误语义；
- 有实际算法、解析、转换、金额精度或边界分支的工具代码。

默认禁止新增测试的对象：

- 纯数据载体、声明类和框架样板：DTO、DO、VO、Projection、枚举、常量、错误码、异常类、Lombok 行为、启动类；
- 无独立业务行为的 Mapper/Repository 接口、配置类、Bean 装配和协议转发；
- Migration 类、Migration SQL、Schema SQL、索引、约束和数据回填脚本；
- 真实 MySQL、Redis、缓存切面、事务/锁、Outbox、MQ、外部服务和 Testcontainers 集成行为。

重要业务规则不应为了避开测试而藏进 Mapper、配置或基础设施类；应将规则放回 Service 或独立业务策略，再从允许范围测试。确实无法通过允许范围内测试或其他验证方式控制风险时，先说明失败场景、替代方案和新增范围外测试的必要性，获得用户明确批准后才能添加。

现有范围外测试属于遗留资产：可以运行，可以在生产契约变化时做最小兼容修改，但不得复制、扩展或把它们当作新测试模板。测试体系重写不属于普通功能需求的顺手重构。

## 实施与测试阶段

默认按以下顺序推进一个稳定、可独立验证的生产代码切片：

1. 完成业务逻辑、公共契约、持久化、异常、权限和适用的一致性处理；
2. 通过 Production Gate；
3. 基于需求、不变量和实际实现形成测试矩阵；
4. 编写自动化测试；
5. 运行相关测试、覆盖率分析和更大范围验证；
6. 修复缺陷与高风险覆盖缺口，直到满足交付门槛。

不得在公共契约和核心流程尚未稳定时，按方法数量提前生成大量测试。以下情况可以先写或同步编写测试：

- Bug 修复先增加能够复现问题的失败回归测试；
- 用户明确要求或方案明确采用 TDD；
- 协议、算法、解析器或状态机适合契约先行；
- 允许范围内的并发业务不变量或历史 Service/Controller 行为需要先用测试固定；
- 其他经方案说明的测试先行场景。

Implementation-First 只约束阶段切换，不允许把所有测试推迟到整个需求末尾。复杂需求应拆成稳定的纵向切片，每个切片分别完成实现、测试和验证。

## Production Gate

进入一个生产代码切片的批量测试实现前，必须确认：

- 需求内的正常、边界、拒绝和依赖失败流程已完成；
- 公共接口、事件、数据库和错误契约已经稳定；
- 输入校验、权限、租户隔离、事务和适用的并发/幂等行为已经实现；
- 没有未解释的 TODO、占位返回、空实现、临时开关或仅为演示的硬编码；
- 生产代码可以通过 mvn compile -q；
- 实现没有发生未经记录的重大设计偏离。

Gate 未通过时继续完成生产实现，不得用测试 Mock 掩盖缺失的业务流程。编译因与本次变更无关的外部问题无法通过时，必须记录具体命令、首个根因和未验证风险，不能自行宣称通过。

## 测试矩阵 Gate

写测试代码前，先列出受影响行为的测试矩阵。L1 可以使用简短列表；L2/L3 应使用技术方案模板中的矩阵，并包含：

- 场景、前置条件和关联需求/不变量；
- 风险优先级；
- 测试形态：Service/业务规则单元测试、Controller Web 契约测试或工具代码单元测试；
- 可观察结果、状态变化和副作用；
- 能够发现错误实现的关键断言；
- 范围外场景不新增单元测试的原因与替代验证。

优先级依次为：关键业务不变量，安全和租户隔离，边界与状态转换，失败与恢复，并发与幂等，正常路径。不得按 public 方法一一生成测试，也不得把“能够调用”“不抛异常”或 assertNotNull 当作核心业务断言。

### Mock 约束

- 只 Mock 当前测试边界之外的依赖，不 Mock 被测对象自身、值对象或需要验证的业务规则。
- 不把 `verify(mock).method(...)` 当作业务正确性的唯一证据；同时断言返回、状态变化、发布内容或错误契约。
- 一个测试出现大量无关 Mock、深层 stub 链或必须知道私有调用顺序时，先检查生产代码职责是否混乱。
- 不使用宽松默认值掩盖遗漏交互；关键依赖失败、超时和返回异常数据必须有明确场景。
- fixture 表达业务含义并保持最小，不复制大段生产对象图或依赖随机执行顺序。

## 测试选择

测试验证可观察行为，而不是私有实现细节：

- 独立业务规则、状态转换、计算和错误映射：快速单元测试。
- Service 编排：隔离数据库、缓存、消息和外部服务等依赖，覆盖正常、拒绝、空结果和依赖失败。
- Controller 契约、校验、鉴权和响应结构：MockMvc/Spring MVC 测试。
- 工具代码：仅测试实际算法、解析、转换、精度和边界分支；纯包装或委托不测试。
- Mapper、SQL、Migration、真实数据库、Redis、事务、锁、缓存切面、Outbox、MQ 和外部系统：当前不新增 `src/test` 测试，使用本规范定义的范围外验证。

允许测试范围内的 Bug 修复应先增加能复现问题的回归测试，再修复实现。范围外 Bug 不得为了满足“先写测试”突破治理边界，必须说明原因、替代验证和未覆盖风险。

## 范围外验证

无需新增单元测试不等于可以跳过验证。根据变更选择最小充分证据：

- Mapper 和自定义 SQL：SQL 审查、参数与租户条件核对、执行计划或受控环境查询；
- Migration/Schema：语法与顺序审查、空库或目标基线演练、表/列/索引/约束检查、回填抽样和前滚/回滚说明；
- Redis、缓存、事务、锁、Outbox 和 MQ：复用现有测试或运维演练，检查原子性、失效顺序、幂等和失败恢复；
- 外部服务：使用已有沙箱、契约样例、日志或人工验证，不在单元测试中伪造其真实可用性；
- 简单声明和框架装配：编译或启动验证即可，不为“执行到一行”创建测试。

不能获得必要环境时，记录具体未验证项、阻塞原因和失败后果。高风险范围外变更若没有足够替代证据，必须取得用户对剩余风险的确认，不能用 Mock 测试冒充真实验证。

## 最低场景

新增或修改业务逻辑至少评估：

- 正常路径；
- 非法输入或业务拒绝；
- not-found/空结果；
- 边界值和分页边界；
- 无权访问和跨租户访问；
- 数据库、缓存、消息或 Provider 失败；
- 重试、重复请求和并发竞态；
- 旧调用方和历史数据兼容。

不是每项都必须生成一个测试，但省略与需求相关的场景必须有合理依据。

## 覆盖率与测试有效性

覆盖率用于发现允许测试范围内的行为遗漏，不能证明业务正确、SQL 语义、事务一致性、并发安全或测试断言有效。以下目标只适用于 Service、Controller 契约、独立业务规则和有实际逻辑的工具代码：

- 上述允许范围内新增或实质修改的行为代码：变更行覆盖率不低于 85%，变更分支覆盖率不低于 80%；
- 上述允许范围内的计费、额度、鉴权、租户隔离等关键业务：变更行覆盖率不低于 90%，变更分支覆盖率不低于 85%；
- 全仓覆盖率作为趋势指标，不要求单次需求偿还无关历史测试债。

DTO/DO、声明类、Mapper、Migration、SQL 和基础设施代码不因覆盖率缺口而补写测试。CI 或 Codecov 的全局/Patch Coverage 与当前治理范围冲突时，报告冲突并请求调整门槛或批准偏差，不得让覆盖率工具扩大测试范围。JaCoCo 类/包覆盖率不能冒充 Git Diff 覆盖率；当前工具无法可靠测量允许范围内的变更覆盖率时：

1. 运行 mvn verify 生成 JaCoCo 报告；
2. 报告受影响类可实际测得的行与分支覆盖情况；
3. 对允许范围内未覆盖代码按业务风险分类，并补齐重要场景；
4. 明确说明变更覆盖率尚未被机器验证，不得声称已达到百分比门槛；
5. 未达目标或无法测量的偏差必须得到用户批准后才能视为完成。

禁止通过空调用、无意义断言、重复相同场景或只测试 Mock 行为提高覆盖率。不得把范围外类排除规则扩大到 Service 或独立业务规则。关键计费、鉴权和额度逻辑在普通覆盖率不足以证明断言有效时，应评估定向变异测试；没有成熟配置时不强制全仓执行。

## 执行顺序

1. Production Gate 运行 `mvn compile -q`。
2. 开发过程中反复运行最小相关测试：`mvn test -Dtest=ClassName`。
3. 修改完成运行所有受影响测试类和 `mvn compile -q`。
4. 以下情况运行 `mvn test`：公共组件、配置、AOP、权限、事务、缓存、数据库 migration、异步/Outbox、Provider 注册或跨模块重构。
5. 需要覆盖率报告时运行 `mvn verify` 并读取实际报告。
6. 交付制品或依赖/构建修改运行 `mvn clean package`。

不得把 `mvn clean package -DskipTests` 当成功验证；它只验证可跳过测试的构建路径。

## 失败处理闭环

测试失败时：

1. 保留失败命令、测试名和首个根因；
2. 单独重跑失败测试，排除套件噪声；
3. 将失败归类为本次回归、错误测试预期、非确定性、环境缺失或仓库既有问题；
4. 修复根因，不允许删除测试、降低断言、无条件延长 sleep 或吞掉异常；
5. 重跑失败测试，再重跑受影响集合；
6. 若修复改变设计或范围，更新计划和相应文档。

外部服务、凭据或基础设施缺失时，允许范围内的单元测试使用已有 fixture/Mock 隔离依赖；现有遗留数据库测试必须使用真实 MySQL，报告具体阻塞，不以 H2 替代。不得新增数据库测试，也不得伪造“测试通过”。

## 完成定义

交付前逐项确认：

- 实现满足需求且没有无关行为变化；
- API、权限、事务、缓存和错误语义已经检查；
- 允许测试范围内的新业务行为有与风险相称的测试；
- 范围外变更已有适当验证证据，或未验证风险已经明确并获得用户批准；
- Production Gate 和测试矩阵 Gate 已完成；
- 相关测试与编译已经实际通过；
- 配置的覆盖率门槛已通过，或偏差和未测量风险已经明确并获得批准；
- 没有秘密、调试输出、临时开关或未解释 TODO；
- DTO/DO 字段中文说明、migration 和运维文档同步；
- 最终报告列出验证命令和结果，明确任何未验证项与风险。
