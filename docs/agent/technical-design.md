# 技术设计与评审规范

本规范约束 L2/L3 变更的仓库调研、技术决策、方案评审和实施追踪。技术方案的价值是在编码前消除关键未知和暴露取舍，不是罗列要新增的类和方法。

## 输出强度

- L1 使用根 AGENTS.md 要求的简短计划，无需独立技术方案。
- L2 必须覆盖 docs/agent/templates/technical-design.md 中的适用部分，可以在任务计划中结构化展示；用户要求或需要长期追踪时再落盘。
- L3 必须使用该模板产出完整方案，保留评审结论和用户批准状态。保存位置由用户或任务约定决定，不得自行新建与项目约定冲突的方案目录。

方案长度应与风险成比例。不得为简单 CRUD 制造大型 RFC，也不得将计费、鉴权或一致性变更降级为文件清单。

## 仓库调研证据

方案中的现状结论必须可追溯。调研至少覆盖：

1. 入口和所有已知调用方；
2. 完整调用链、模块边界和依赖方向；
3. 数据权威来源、Schema、索引、事务和并发控制；
4. 缓存、异步事件、外部依赖和故障处理；
5. 权限、租户隔离、兼容性约束和既有运维路径；
6. 相似实现、可复用能力、邻近测试和已知技术债。

每个重要结论都应附具体文件、类、方法、配置项或数据对象。将调研结果分为：

- **已验证事实**：能被仓库、配置、测试或用户明确需求证明；
- **待验证假设**：尚无足够证据，但可以通过调研、实验或测试确认；
- **开放问题**：取决于产品语义、风险接受或外部条件，必须由用户或责任人决定。

不得将假设写成已确认需求，也不得虚构现有组件、接口、配置或仓库行为。

## 需求与不变量

在设计解决方案前，先定义：

- 问题、业务目标、非目标和可观察验收条件；
- 功能需求、性能/可用性/一致性等非功能需求；
- 金额、额度、权限、状态转换和租户隔离等不可被破坏的业务不变量；
- 可接受的陈旧、重复、延迟、少量超限或部分失败语义；
- 必须保持的 API、数据、事件、配置和运维兼容性。

关键语义不明时必须先暴露问题。例如“预算不得超支”在未确定硬上限还是近实时软上限前，不得直接选择分布式预留或事后扣费方案。

## 架构决策

对每个重要决策记录：

1. 需解决的问题和已确认约束；
2. 有意义的候选方案，包括“保持现状”或更简单的方案；
3. 正确性、复杂度、可维护性、扩展性、性能和运维成本上的取舍；
4. 选定方案、理由和明确接受的缺点；
5. 证明该决策成立的测试、指标、故障演练或验收方法。

只比较真正可行的候选方案，不为满足模板虚构选项。优先使用已有基础设施；替换现有能力必须说明兼容和迁移成本。

## 条件式设计检查

以下问题都必须被评估，但只有适用时才设计对应机制。L3 对不适用项简要说明排除依据。

### 边界与抽象

- 能力应归属哪个领域或模块，数据由谁维护？
- 哪些是已知变化点，哪些只是假想需求？
- 现有抽象是否能复用，新接口或设计模式是否有多实现、替换、边界或测试价值？
- 业务策略是否与持久化、外部 SDK 和传输协议分离？

### API、权限与兼容性

- 主体、权限、资源所有权和租户隔离在哪个权威位置校验？
- 输入、输出、错误、幂等和版本语义是什么？
- 旧路径、字段、枚举、默认值和调用方如何兼容或迁移？

### 数据、事务与并发

- 权威数据源、一致性模型和事务边界是什么？
- 唯一约束、索引、迁移、回填和回滚/前滚策略是什么？
- 共享状态会发生哪些竞态，使用原子 SQL、唯一约束、乐观锁、悲观锁还是幂等键？
- 重试、超时、进程崩溃和部分成功时如何恢复？

### 缓存与性能

- 读取频率、数据量、查询/远程成本和延迟目标是什么？
- 可接受多少陈旧，Key 基数、租户隔离、TTL 和失效边界是什么？
- Redis 不可用、热点、穿透和击穿时的行为是什么？
- 如果查询低频、成本低或强实时，优先不缓存并记录理由。

### 异步与外部依赖

- 默认消息可能至少投递一次，消费幂等、顺序、重试、死信和积压如何处理？
- 数据库与消息的双写一致性如何保证？优先复用现有 Outbox。
- 外部调用的连接/响应超时、可重试错误、最大重试、取消、降级和重复计费风险是什么？
- 不得在未证明跨边界保证时声称 exactly-once。

### 可观测、发布与恢复

- 哪些日志、指标、追踪、告警或审计记录能验证方案并定位失败？
- 敏感字段如何脱敏，基数和日志量是否可控？
- 如何分阶段发布、兼容旧数据、检测异常并回滚或前滚？

## 评审规则

评审者的目标是找出方案可能失败的原因，不是证明起草者正确。审查顺序：

1. 需求正确性和完整性；
2. 与实际仓库的兼容性；
3. 数据一致性、并发和幂等；
4. 故障处理、恢复和可观测性；
5. 安全、权限和租户隔离；
6. 复杂度、可维护性、扩展性和运维成本；
7. 测试、验收、发布和回滚的可执行性。

每个发现必须包含严重级别、受影响部分、问题、证据或可复现失败场景以及修正建议：

- **P0**：可造成数据破坏、越权、重大资损或系统性不可用；
- **P1**：关键需求无法保证，或存在实质性一致性、恢复、兼容或安全缺陷；
- **P2**：不阻断正确性，但存在有证据的可维护性、性能、可测试性或运维风险。

不得为满足发现数量虚构问题，也不得只因个人风格不同阻断方案。

评审状态：

- **BLOCKED**：存在未解决 P0/P1 或关键开放问题；
- **NEEDS_REVISION**：方向可行，但尚需实质修订；
- **READY_FOR_HUMAN_REVIEW**：L3 已无已知阻断问题，等待用户最终批准；
- **IMPLEMENTATION_READY**：L2 已消除阻断问题，或 L3 已通过独立评审并获得用户批准。

L3 评审者不得仅依赖起草者摘要，应同时获取原始需求、方案和支撑关键结论的仓库上下文。独立评审可以由另一个 Agent 或人工评审者完成，但不能代替 L3 的用户批准。

## 追踪与偏离

- 每个关键需求或不变量必须关联到设计决策、实现任务和验证场景。
- 实施发现方案事实错误、需求变化或验证无法执行时，先更新方案。
- 不改变契约和风险的局部实现细化可直接记录。
- 改变 API、数据模型、权威数据源、事务/一致性、安全边界、关键技术选型或验证策略属于重大偏离，必须重新评审；L3 还需重新获得用户批准。
