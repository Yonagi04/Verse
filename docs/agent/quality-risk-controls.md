# 常见质量风险控制矩阵

本文件把 Verse 常见失败模式转换为 Harness 控制。优先级表示默认严重度；具体变更可因数据、资损、安全和影响面升级，但不得无依据降级。

## P0：实施前必须消除

| 风险 | 调研与设计要求 | 实施约束 | 最低验证证据 | 阻断条件 |
| --- | --- | --- | --- | --- |
| 业务语义理解不足 | 写明角色、用例、状态、前置条件、不变量、拒绝条件和权限；状态超过 3 个使用状态表/图 | 业务规则集中在权威位置，不以 Controller/SQL 分支拼凑 | 正常、拒绝、边界、非法状态、越权和重复请求场景能观察状态与副作用 | 关键状态转移、权限或数据权威仍是猜测 |
| 数据库设计不合理 | 定义每张表单一职责、主键/唯一约束、字段来源、生命周期、基数、读写模式；建立“查询模式—索引”矩阵 | 避免万能表、重复真相、无来源冗余字段；冗余必须有同步机制和重建方式 | Schema/SQL 审查、约束检查、代表性数据量下 EXPLAIN、迁移演练或明确替代证据 | 表职责、数据权威、唯一性或主要查询索引未定义 |
| 事务与一致性问题 | 列出 DB、Redis、MQ、外部系统的权威关系、事务边界和每个部分失败点 | DB 为权威时缓存可重建；DB+MQ 使用 Outbox；消费幂等；不得把远程调用伪装为本地原子事务 | 失败矩阵覆盖提交前后崩溃、缓存失败、重复/延迟消息、重试和恢复 | 存在双写但没有失败恢复、幂等或对账策略 |

## P1：Production Gate 必须检查

| 风险 | 强制控制 | 需要留下的证据 |
| --- | --- | --- |
| 过度设计 | 每个新接口、抽象、模式、中间件必须对应已知变化点或边界；同时比较直接实现 | 方案写明更简单候选为何不足；简单 CRUD 默认直接实现 |
| 不遵守现有代码风格 | 调研同层至少一个可靠实现和公共约定；禁止把历史缺陷当规范，也禁止创造第三套异常/命名/分层 | 引用复用的类、约定或明确说明为何偏离 |
| 缺乏变更范围控制 | 计划列出目标文件/模块和非目标；新增范围必须与需求有直接因果关系 | 最终实际范围与计划对照，偏离有记录 |
| 代码重复与抽象失衡 | 先搜索现有能力；区分业务知识重复与偶然代码相似；关键不变量尽早集中，普通重复遵循三次原则 | 说明复用点或不抽象理由；不得新增 `CommonUtil` 式收容类 |
| 测试质量差 | 测试矩阵从业务风险出发；Mock 只隔离边界，不把 Mock 调用次数当业务正确性 | 关键断言覆盖结果、状态和副作用；包含拒绝/边界/失败路径 |
| 错误处理不完整 | 为每个外部/异步边界定义超时、可重试错误、次数、退避、幂等、降级和最终失败 | 失败测试或替代演练、错误码映射、日志/指标和恢复路径 |
| 对现有代码理解不足 | 修改公共契约前搜索所有调用方、实现、配置、序列化、缓存和测试 | 调研证据列出文件与符号；未知调用方作为开放问题 |

## P2：设计和交付必须闭环

| 风险 | 强制控制 | 需要留下的证据 |
| --- | --- | --- |
| 技术文档与代码脱节 | 方案决策关联实施任务和验证场景；重大偏离先更新方案再实施 | 技术方案“实施偏离”及最终对照；过期文档同步修改或删除 |
| 性能意识不足 | 查询、循环、分页、批量、缓存和事务评估数据上界；禁止 N+1、全表加载、无界集合/队列/缓存和长事务 | EXPLAIN/指标/基准/代码上界之一；没有测量不得声称优化成功 |

## 数据库设计检查表

涉及表、字段或查询时，方案至少回答：

1. 这张表只负责什么，明确不负责什么？权威事实来自哪里？
2. 主键、业务唯一键、租户隔离键、状态和审计字段是什么？
3. 字段是事实、快照、派生值还是缓存？派生/冗余如何同步、校验和重建？
4. 主要读写 SQL、预期基数、排序和分页方式是什么？每个索引支持哪个查询？
5. 唯一约束、并发写、删除生命周期、历史数据和迁移兼容如何处理？
6. 是否存在大字段、冷热混放、过宽行、无界增长或需要归档/清理的问题？

## 范围与风格 Gate

- 开始：列出预计修改文件/模块、公共契约、调用方和明确非目标。
- 中途：新发现的必要改动先更新计划；与目标无直接因果关系的清理停止并单独记录。
- 结束：对照计划检查实际 diff；不得混入格式化全文件、批量重命名或无关抽象替换。
- 风格：优先复用仓库中已验证的 Result、错误码、DTO/DO、Mapper、缓存、Outbox 和 Provider 边界；若现有样例本身违反上级规范，修复局部根因而不是复制。
